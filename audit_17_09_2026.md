**Constats Sécurité**

**Critique** - Inscription publique avec rôle choisi par l’utilisateur.  
Dans [auth_schema.py](/home/precieux/AgriOriginal/backend/src/presentation/schemas/auth_schema.py:25), le payload `/api/auth/register` accepte directement `role`, puis [auth_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/auth_routes.py:28) crée l’utilisateur avec ce rôle. N’importe qui peut donc s’inscrire en `admin`, `exporter` ou `controller`. Il faut fixer un rôle par défaut côté serveur, par exemple `exporter` ou `controller`, et réserver la création d’admin à un compte déjà admin ou à un script d’initialisation.

**Critique** - Secret JWT faible par défaut.  
[config.py](/home/precieux/AgriOriginal/backend/config.py:20) et [.env.example](/home/precieux/AgriOriginal/backend/.env.example:10) utilisent `change-me-in-production-please`. Si ce secret reste en prod, les tokens JWT peuvent être forgés. À corriger en refusant le démarrage hors développement si `JWT_SECRET` vaut la valeur par défaut ou est trop court.

**Élevé** - Plusieurs endpoints exposent les données sans authentification.  
Les lots sont listables publiquement dans [lot_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/lot_routes.py:49), les mesures dans [measurement_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/measurement_routes.py:37), et les alertes actives dans [alert_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/alert_routes.py:22). Si ces données sont métier ou client, il faut ajouter `@require_auth` ou `@require_role`, puis filtrer par propriétaire/exportateur.

**Élevé** - Endpoint d’ingestion IoT ouvert.  
[measurement_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/measurement_routes.py:17) permet de poster des mesures sans authentification appareil/API key. Un attaquant peut injecter de fausses mesures et créer des alertes. Il faudrait une clé par device, une signature HMAC, ou au minimum un token dédié machine-to-machine.

**Moyen** - CORS ouvert à toutes les origines.  
[app.py](/home/precieux/AgriOriginal/backend/app.py:16) fait `CORS(app)` sans restriction. Pour la prod, limite aux domaines frontend autorisés, par exemple `CORS(app, origins=[config.public_base_url])`.

**Moyen** - Les paramètres `limit` peuvent provoquer des erreurs 500.  
Exemples : [measurement_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/measurement_routes.py:39), [alert_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/alert_routes.py:17), [lot_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/lot_routes.py:52). `?limit=abc` déclenche `ValueError`. Ce n’est pas une fuite critique, mais c’est exploitable pour générer des erreurs et polluer les logs. Ajouter un parseur sûr qui renvoie `400`.

**Moyen** - Les droits ne sont pas vérifiés au niveau ressource.  
Un utilisateur `EXPORTER` peut modifier le statut de n’importe quel lot via [lot_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/lot_routes.py:73), sans vérifier que `lot.exporter_id == g.current_user_id`. Même remarque pour la résolution d’alertes dans [alert_routes.py](/home/precieux/AgriOriginal/backend/src/presentation/routes/alert_routes.py:29). Il faut contrôler l’appartenance ou les permissions par ressource.

**Faible à moyen** - Claims JWT peu validés.  
[token_service.py](/home/precieux/AgriOriginal/backend/src/domain/services/token_service.py:37) transforme les claims manquants en `"None"`. Le middleware accepte ensuite tout token décodé, puis compare le rôle dans [auth_middleware.py](/home/precieux/AgriOriginal/backend/src/presentation/middleware/auth_middleware.py:32). Mieux vaut exiger `sub`, `role`, `email`, vérifier que `role` est dans `UserRole`, et éventuellement vérifier que l’utilisateur existe encore.

**Points Positifs**

Le hash de mot de passe est correct pour une base simple : sel aléatoire, PBKDF2, comparaison constante dans [password_hasher.py](/home/precieux/AgriOriginal/backend/src/domain/services/password_hasher.py:13). Les accès Mongo utilisent des filtres structurés, pas de concaténation de requêtes. Les ObjectId invalides sont globalement capturés.

Je n’ai pas modifié le code : j’ai fait une revue statique de sécurité. Les deux corrections prioritaires sont clairement l’inscription avec rôle libre et le secret JWT par défaut.
